# SofaPaint measurement-review loop — the one-ZIP workflow

## Goal

Your successful loop (PDF → measurements → Shenzhen email → focused images → customer reply) currently needs several copy-paste hops between SofaPaint, GPT, and the quick-links tool. SofaPaint becomes the hub: **one drafting bundle OUT to GPT, one reply bundle back**, with frames and questions identified explicitly — no retyped codes, no ambiguity about which image answers which question. Version-1 requests keep working exactly as today. SofaPaint-side only; the quick-links exporter fixes become a checklist plus an artifact contract for that tool's own repo.

## Phase 1 — One-ZIP loop (the core smoothing)

**Request spec v2 (additive, strict versioning)** — in `src/modules/ui/measurement-check-request.ts`:
- `specVersion: 1` (or absent) behaves exactly as today. `specVersion: 2` enables the additions below. Anything > 2 fails with an explicit error (today unknown keys are silently stripped — that becomes a hard error).
- v2 additions: per-page `frame` (tab id or frame index) + `questionIds: ["Q1"]`; optional top-level `questions: [{ id, text }]` and `case: { ticketId?, orderId? }`.
- Catalogue gains a per-view `frames: [{ scopeKey, tabId, title, codes }]` array (additive — `views`/`codes` untouched), so repeated A/B/C codes across seat/back/pillow frames are individually selectable.
- Frame resolution: v2 `frame` → exact scope. A **v1** request whose codes exist in multiple frames of a view now reports a new `ambiguous-frame` issue instead of silently matching the first (matches your brief: surface, don't assume).

**Production notes box** — small optional textarea in the check dialog ("production email / notes") held in dialog state; included as `context/production.json` in bundles.

**"Build GPT drafting bundle"** — new dialog action (validates first, captures images as today):
`drafting-<project>-<date>.zip` per your brief's contract, adapted:
- `manifest.json` — schemaVersion, case (ticket/order from `metadata.externalSources.gorgiasTickets` when present), created, completeness, asset list.
- `context/catalogue.json` (v2), `context/production.json`, `context/measurements.json` (resolved pages, values, unit, customer notes from `metadata.measurementNotes`).
- `selection/request.json` (the accepted request) and `selection/questions.json` (numbered question groups ↔ page/image mapping).
- `images/` — the focused PNGs, named `q<questionId>-<view>-<frame>.png` when questionIds exist (else today's `check-NN-view`).
- `reply/skeleton.txt` — numbered questions + image refs for GPT to fill.

**"Load reply draft" → "Export reply bundle"** — second file input accepts GPT's returned `email.txt` (+ optional `internal-notes.txt`); the dialog validates: every question id covered, every referenced image exists, ordering derivable. Then exports `reply-<project>-<date>.zip`: `reply/email.txt`, `reply/email.html` (numbered paragraphs, images inline in order), `reply/manifest.json` (question→image ordering), `images/` (real bytes — the exact failure mode your brief flags in the quick-links export), `reply/internal-notes.txt`. That ZIP is what you attach in Gorgias — and the artifact the exporter tool should consume wholesale.

## Phase 2 — Trust + loop memory

- **Notes flow into exports**: stored measurement notes render inside focused-PDF table rows (e.g. J1: `27" (26" to floor)`) so Shenzhen sees the customer's context without extra typing.
- **Session memory**: last check sessions stored in project metadata (`checkSessions`: request, questions, image names, reply, created — add to `sofa-metadata.js` defaults/normalize). Reopening the dialog lists recent sessions; re-export or follow-up without re-pasting.
- **Answer capture**: per question, paste the customer's answer text → stored against the question in the session; unanswered questions stay visibly open; changed values flagged. Lightweight open/answered only — no state machine.

## Phase 3 — Outside this repo (documented, not built now)

- Quick-links exporter checklist: outbound-evidence, complete-image-bytes, explicit-image-order, attachment-completeness, asset-integrity — its fix is to attach the SofaPaint reply bundle verbatim.
- In-repo extension thread-export (its existing fetch/hash plumbing supports it) — later.
- Authorised Gmail/Gorgias imports and automated answer reconciliation — later.

## Implementation files

- `src/modules/ui/measurement-check-request.ts` — v2 schema + version guard, frames in catalogue/resolver, `ambiguous-frame` issue, bundle builders (JSZip), reply import/validation, sessions, dialog UI additions.

- `tests/unit/measurement-check-request.test.ts` — v2 parsing/version guard, frame selection hits frame-2 strokes, v1 multi-frame ambiguity warning, bundle manifest shape, reply validation failures, notes in measurements context.

## Acceptance checks

- Your Verellen reference case: paste the v1-style request → identical pages as today; the v2 version of the same request (frames + questionIds) produces per-frame images named by question.
- A v3 spec errors explicitly; a v1 request with codes spanning two frames reports `ambiguous-frame` rather than first-match.
- The drafting bundle unzips standalone and contains every question's image bytes; the reply bundle's manifest, email.html, and images agree on order.
- Re-running with unchanged inputs rewrites the same bundle (no duplicate sessions).
- 40 1/2" ↔ 102.87 cm stays exact; notes travel with their measurement everywhere they appear.
